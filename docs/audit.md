# Аудит решения перед защитой

Независимая проверка «на злого члена жюри»: что снимут и за что.
Дата: 3 сентября 2026. Стопкод: 6 сентября.

**Состояние на момент аудита.** Ветка `main`, есть `origin`, последний коммит —
`566ab1c` «HTML-дашборд объяснимости, чистка конфигурации». Рабочее дерево правилось
прямо во время проверки, и часть находок была закрыта по ходу — они вынесены в
отдельный раздел «Закрыто во время аудита». Всё остальное перепроверено повторно на
дереве после правок; каждое утверждение сопровождается командой и её выводом.

Что запускалось:

```
ruby bin/route plan | run | compare | replay | finalize   -> все отрабатывают, rc=0
ruby scripts/validate_10.rb routing_decisions.json        -> Пройдено 29, Ошибок 0, Предупр. 0
rake test                                                 -> 249 runs, 1664 assertions, 0 failures, 0 errors, 0 skips
ruby bin/dashboard                                        -> out/dashboard.html, 178 КиБ
```

Плюс 26 синтетических прогонов на подложных очередях и подложных `providers.json`.

**Итог оценки:** эксперты ≈ **86 / 100**, техжюри ≈ **131 / 140**, отраслевое ≈ **13 / 20**.
Зачётная сумма (ТЖ + ОЖ) ≈ **144 / 160**.

Решение сильное. Из четырнадцати оставшихся замечаний только два действительно опасны,
и оба — про боевую очередь, а не про качество алгоритма.

## Д-2. При отсутствии маршрута из решения пропадает обязательное поле — риск 20 баллов

`Decision#to_h` заканчивается `.compact` (`lib/routing/decision.rb`). Если
`selected_provider` равен `nil`, ключ **исчезает из JSON целиком**. Автопроверка
организаторов проверяет именно наличие ключа:
`errors << "отсутствует поле #{field}" unless decision.key?(field)`
(`scripts/validate_10.rb:56`).

```
$ ruby bin/route run --providers p_alldown.json --decisions a.json   # все провайдеры inactive
$ ruby -rjson -e 'd=JSON.parse(File.read("a.json")); puts d[0].keys.inspect'
["operation_id", "attempts", "simulated_result", "latency_sec", "amount", "bank",
 "selection", "cascade", "events"]                      <- selected_provider отсутствует

$ ruby scripts/validate_10.rb a.json | grep -c "отсутствует поле selected_provider"
10
```

Ситуация достижима не только на выдуманном `providers.json`. На настоящих данных кейса
и очереди из 60 заявок без `created_at`:

```
$ ruby bin/route run --queue q_nodate60.json --decisions n.json
$ ruby -rjson -e 'd=JSON.parse(File.read("n.json"))
  puts "без ключа selected_provider: #{d.count{|o| !o.key?("selected_provider")}}/#{d.size}"'
без ключа selected_provider: 25/60
```

На тысяче заявок — 957 из 1000. Механизм разобран в Д-9.

Смягчающее обстоятельство: `bin/route finalize` это ловит
(`decisions.all? { |d| d.selected_provider }`) и возвращает код 1 с текстом «Не сдавать».
Но файлы к этому моменту уже записаны в корень, а времени в час X нет. Строгий вариант
`out/routing_decisions.strict.json` ключ сохраняет (`to_strict_h` без `.compact`) — но
сдаётся не он.

**Починка:** убрать `.compact` в `to_h` либо явно писать `"selected_provider" => nil`.
И отдельно решить, что вообще должно стоять в этом поле, когда маршрута нет: `null`
формально удовлетворит проверку структуры, но провалит проверку «выбранный входит в
список допустимых». Двадцать минут.

## Д-9. Скользящее окно интенсивности плюс монотонные часы душат роутинг — корень Д-2 и Д-3

Числа `requests_per_minute_limit` в `config/provider_overlays.yml` (12 / 3 / 20 / 5)
выведены из пропускной способности, но применяются к скользящему окну по времени
заявки. `Clock#advance_to` берёт `max(@now, stamp)` — «время не идёт назад». На
неотсортированной очереди это означает, что все «опоздавшие» заявки получают одну и ту
же отметку и валятся в одно окно.

История кейса неотсортирована:

```
$ ruby -rcsv -rtime -e 'r=CSV.read("data/operations_history.csv",headers:true)
  t=r.map{|x| Time.parse(x["created_at"])}
  g=t.each_cons(2).map{|a,b| (b-a).round}
  puts "отсортирована: #{g.all?{|x| x>=0}}, отрицательных интервалов: #{g.count{|x| x<0}}, минимум: #{g.min}"
  puts "максимум заявок в честном 60-с окне: #{t.map{|x| t.count{|y| y>x-60 && y<=x}}.max}"'
отсортирована: false, отрицательных интервалов: 48, минимум: -11390
максимум заявок в честном 60-с окне: 3
```

Реальная интенсивность — 3 заявки в минуту на всю систему, а лимит срабатывает 134 раза
на 100 операциях реплея.

Прямая демонстрация: одна и та же очередь, переставленная задом наперёд, даёт другой
результат по тем же заявкам с теми же метками времени.

```
$ ruby bin/route run --queue q_like30.json       # 30 заявок, шаг 30 с, по возрастанию
  rate_limit_exceeded=0   {"vipay"=>11, "quickpay"=>14, "payflow"=>5}
$ ruby bin/route run --queue q_like30_rev.json   # те же 30, порядок обратный
  rate_limit_exceeded=10  {"vipay"=>11, "quickpay"=>15, "payflow"=>2, "spacepayments"=>2}
```

Тот же механизм при отсутствии `created_at`: `Clock` двигает виртуальные часы на 1 с,
то есть выдаёт 60 заявок в минуту, и лимиты 3/12/20 отсекают почти всех, включая
self-провайдера с лимитом 5.

```
$ ruby bin/route run --queue q_nodate60.json   # 60 заявок без created_at
  без ключа selected_provider: 25/60
$ ruby bin/route run --queue q_same60.json     # 60 заявок с одинаковым created_at
  без ключа selected_provider: 26/60
```

Что виновата именно накладка, а не логика роутинга, доказывается её отключением:

```
$ ruby bin/route run --queue q_same60.json --overlays /dev/null
  без ключа selected_provider: 0/60
$ ruby bin/route run --queue q_1000.json --overlays /dev/null
  без ключа selected_provider: 0/1000
```

**Это главный риск боевой сдачи.** `operations_queue_test.json` выдадут за час до
стопкода, и никто не обещал, что он отсортирован, что у заявок есть `created_at` и что
их будет ровно десять.

**Починка, по возрастанию стоимости:**
1. Сортировать очередь по `created_at` перед прогоном, факт исходной неотсортированности
   писать в `data_quality`. Двадцать минут, снимает половину проблемы.
2. Шаг виртуальных часов при отсутствии `created_at` — из конфигурации, по умолчанию не
   1 с, а `60 / min(requests_per_minute_limit)`. Десять минут.
3. Пересчитать `requests_per_minute_limit` от пропускной способности, а не от медианы
   задержки: 3 заявки в минуту для payflow при `in_progress_count_limit = 8` — в разы
   жёстче, чем декларирует сам провайдер. Полчаса на пересчёт и обоснование.

объяснить одной строкой: история не соблюдала целевые доли по объёму и не упиралась в

## Д-4. Поле `score` противоречит порядку ранжирования — ТЖ-3.1, ТЖ-4.1

`Scorer#weighted_total` считает взвешенную сумму по всем целям, а `Scorer#order` в
режимах `lexicographic*` сортирует по эшелонам. В выгрузку уезжает `score` — число, по
которому выбор **не** производился.

```
$ ruby bin/route run --profile capacity_saver --decisions cs.json
$ # op_101, выбран quickpay:
   quickpay: score=0.4507  tiers={"1"=>0.7692, "2"=>0.2286, "3"=>0.4}
   vipay:    score=0.6847  tiers={"1"=>0.4429, "2"=>0.8884, "3"=>0.6}
   payflow:  score=0.4977  tiers={"1"=>0.2308, "2"=>0.6952, "3"=>0.5}
```

Победил кандидат с наименьшим `score` из трёх. Объяснение лежит в `tiers`, но читателю
надо самому догадаться, что спор решился первым эшелоном. Число операций с такой
инверсией по профилям: `capacity_saver` — 5 из 10, `share_strict` — 1,
`conversion_first` — 1, `balanced` и `cascade_only` — 0.

**Починка:** не печатать `score` в лексикографических режимах либо добавить рядом
`decisive_tier` и строку «спор решён эшелоном 1». Двадцать минут.

## Д-6. Ограничение по валюте не срабатывает никогда — ТЖ-1.1, Э-1.1

`Currency#check` уходит в `skip`, если у провайдера пустой список валют, а поля

## Закрыто во время аудита

Эти дефекты были найдены и к концу проверки уже исправлены в рабочем дереве —
перечислены, чтобы не искать их второй раз и чтобы правки не откатились.

* **Затирание записи об отказе.** `Cascade#records` индексировался по `provider_id`, и
  повторная попытка на том же провайдере перезаписывала его `declined_record`: из
  `attempts` исчезал сам факт отказа, `sequence` шёл `[1, 2, 4]`, а `skip_reasons`
  недосчитывал `provider_declined`. Сейчас `sequence op_103 = [1, 2, 3, 4]`,
  `provider_declined` встречается в выгрузке.
* **Синоним `daily_turnover_max`.** Поле было перечислено и в списке синонимов
  `daily_amount_limit`, из-за чего одно значение заполняло оба и правило
  `daily_turnover_max` не могло сработать никогда. Сейчас поля читаются раздельно,
  проверено на подложном `providers.json`, где есть только `daily_turnover_max`.
* **Мёртвые ключи конфигурации.** `simulation.forced_decline_rate` и
  `goal_relaxation.reallocate_unreachable_share` объявлялись и не читались; теперь оба
  читаются кодом.
* **`rake test` был красным** (`AcceptanceTest#test_two_runs_with_the_same_seed_produce_byte_identical_decisions`
  искал файл не по тому имени). Сейчас: 249 runs, 0 failures, 0 errors, 0 skips.
* **Мусор в корне репозитория.** Артефакты браузерной автоматизации `.playwright-mcp/`
  и `*.strict.json` лежали в корне `main`; убраны, строгие варианты переехали в `out/`.

## Что проверено и оказалось в порядке

Чтобы не тратить на это время повторно.

* **Детерминированность.** Два прогона подряд — `cmp` на `routing_decisions.json` и
  `routing_report.json` совпадает побайтово. Зерно симулятора собирается из
  `seed|operation_id|provider|attempt_no`, то есть не зависит от порядка обработки.
* **Перестановка очереди.** Из 10 операций меняет провайдера ровно одна (op_106:
  vipay → quickpay). Это правильное поведение — цели по долям считаются от накопленного
  состояния, — но в README об этом ни слова, а спросить могут. Одна строка снимет вопрос.
* **Контракт вывода на сданных файлах.** `simulated_result` только из
  {approved, rejected, expired}; `decision` только из {selected, skipped}; ни одной
  операции с пустым `attempts`; ни одной, где выбранного нет среди `attempts` как
  `selected`; ни одной с двумя `selected`; `latency_sec` — целое неотрицательное.
* **Согласованность отчёта и решений.** Сумма `skip_reasons` равна числу записей
  `skipped`; `distribution` покомпонентно сходится с фактическими `selected_provider`;
  `total_operations` равно числу записей; `sum(share_pct) = 100.0`; рекомендации
  ссылаются на числа из этого же отчёта.
* **`min_max_normalize` при одном кандидате** возвращает 0.5 и помечено комментарием —
  фактор честно не притворяется значимым. При нулевых весах у всех целей
  `weighted_total` возвращает 0.0 без деления на ноль, порядок разрешает `tie_break`.
* **Битый вход.** Пустой файл, невалидный JSON, отсутствующий файл, провайдер без
  идентификатора, `providers: []` — внятное сообщение, код возврата 2, без трассировки стека.
* **Подмена `providers.json`.** Прогнаны 12 вариантов: `status: inactive` у одного и у
  всех; `exclude_banks: true` (чёрный список читается правильно, vipay начинает брать
  gazprombank и raiffeisen); нулевые реквизиты; отсутствующий `merchant_margin_pct`
  (правило корректно становится неприменимым, а не нарушенным); единственный провайдер;
  только self-провайдер; дубликат провайдера; нулевые `traffic_percentage`. Падений нет
  ни в одном случае.
* **Ограничения кейса.** Внешних гемов нет вовсе, `Gemfile` отсутствует как класс, весь
  код на Ruby (8 147 строк `.rb` против 1 539 строк шаблонов `.erb`), ни одной
  ML-зависимости и ни одного обращения к внешней модели.

## Мелочи, которые дёшево убрать

* `distribution[].deviation_pct` — на самом деле пункты, а не проценты; `deviation_pp`
  читается однозначно и совпадает с формулировкой ТЗ.
* `provider.rb` — строка из одних пробелов перед `false` в `blacklist_mode?`.
* При `--decisions` с путём вне репозитория строгий вариант всё равно уезжает в `out/`
  рядом с проектом — неожиданно, но безвредно.
* `Reasons::CATALOG["lower_score"]` достижим только в ветке, где выбранного нет вообще,
  и текст «уступил по итоговому скорингу» там неверен.
* `outcomes.avg_latency_sec = 156.3` при `avg_latency_sec` провайдеров 29–52: задержка
  суммируется по всем попыткам каскада. Трактовка законная, но нигде не объявлена — одна
  строка в README снимет вопрос «почему у вас выплата идёт две с половиной минуты».

## Чего делать не надо

* **Догонять целевые доли на длинной очереди.** Отчёт уже доказывает, что цель 35% на
  payflow недостижима сверху (коридор 10..30% по свободному дневному лимиту), а 25% на
  quickpay — недостижима снизу (коридор 30..90%, он единственный допустимый в 30%
  заявок). Это сильный аргумент, а не слабость; его надо произносить вслух первым, а не
  пытаться «исправить» распределение.
* **Добавлять новые стратегии.** Восьми хватает с запасом. ТЖ-2 упирается не в число
  целей, а в доказательство, что каждая на что-то влияет, — это пункты 6 и 10.
* **Трогать `Scorer`, `ProviderState` и `Statistics`.** Самые аккуратные части решения;
  правка в них за двое суток до стопкода — чистый риск без выигрыша.
