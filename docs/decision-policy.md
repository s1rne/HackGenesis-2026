# Политика принятия решения

Формальное описание того, как роутер выбирает провайдера. Документ написан так,
чтобы его можно было читать вместо кода: каждая формула здесь сверена с
исходником, каждое число взято из настоящей выгрузки прогона и воспроизводится
на калькуляторе.

Собранную политику всегда можно увидеть глазами:

```bash
ruby bin/route plan     # порядок ограничений, состав целей, эшелоны, веса, тай-брейк
```

Источники: `config/routing.yml` (все настройки), `lib/routing/scorer.rb`
(согласование), `lib/routing/cascade.rb` (порядок попыток),
`lib/routing/statistics.rb` (нормализация), `lib/routing/fleet.rb` (цели по
долям), `lib/routing/analytics/achievability.rb` (достижимость).

---

## 1. Два вопроса и два механизма

Решение разбито на два независимых вопроса, и это разделение — не стилистика,
а условие корректности.

| | Жёсткое ограничение (допуск) | Мягкая цель (предпочтение) |
|---|---|---|
| Вопрос | Можно ли вообще отправить эту заявку этому провайдеру? | Кого предпочесть среди тех, кому уже можно? |
| Ответ | да / нет + код причины | число, «больше — лучше» |
| Вес | нет | есть (`weight`) |
| Сравнивает провайдеров | нет | да |
| Код | `lib/routing/constraints/` | `lib/routing/strategies/` |
| Реестр | 11 правил, порядок из конфигурации | 10 целей, эшелоны и веса из конфигурации |

Допуск вычисляется первым и целиком: `Cascade#hard_filter` проходит правила в
порядке из `hard_constraints`, первое нарушение прекращает проверку по этому
провайдеру и записывается в `attempts` как `decision: "skipped"` с кодом причины.
Скоринг видит только тех, кто прошёл.

**Что было бы, если бы их смешали.** Единственный способ смешать — превратить
допуск в большой штраф в общей сумме. Тогда:

* нарушение перестало бы быть абсолютным: провайдер с превышенным дневным
  лимитом, но идеальной конверсией и огромным недобором по доле, набрал бы
  больше «штрафа минус бонусы» — и заявка ушла бы туда, где её физически
  нельзя провести. Величина штрафа стала бы настройкой, определяющей
  законность операции;
* исчезла бы причина отказа. Сейчас на каждого исключённого приходится строка
  вида `amount_exceeds_limit: 150000 > limit_amount_max 100000`. В смешанной
  схеме на его месте было бы «суммарный скор ниже», из чего нельзя понять ни
  что чинить, ни кто виноват;
* сломалась бы нормализация. Веса целей нормализуются по пулу кандидатов
  (см. §2): достаточно одного заведомо недопустимого провайдера, чтобы
  растянуть шкалу и изменить нормализованные оценки всех остальных;
* стал бы невозможен расчёт достижимости (§7): он строится ровно на том, что
  множество допустимых провайдеров для заявки определено однозначно и не
  зависит от текущих весов.

## 2. Формула скоринга

### Три шага

**Шаг 1. Сырая величина.** Каждая цель отвечает за одну величину и возвращает
её в своих собственных единицах — `raw_score(context)`, «больше — лучше»:
`count_share` — недобор в штуках заявок, `volume_share` — долю недобора по
деньгам, `conversion` — нижнюю границу интервала Вильсона, `cascade_priority` —
отрицательный номер приоритета, `margin` — разрыв маржи в п.п. Возврат `nil`
означает «цель к этому провайдеру неприменима».

**Шаг 2. Нормализация по пулу.** Складывать рубли с процентами нельзя, поэтому
`Scorer#build_matrix` собирает вектор сырых значений всех кандидатов по одной
цели и приводит его в `0..1` через `Statistics.min_max_normalize`:

```
finite = значения, которые не nil и конечны
если finite пуст                       -> все получают 0.5
min = min(finite), max = max(finite), span = max - min
если |span| < 1e-12                    -> все получают 0.5
иначе                                  -> norm(v) = clamp((v - min) / span, 0, 1)
nil сохраняется как nil и в Scorer превращается в 0.5
```

Нейтральные `0.5` при совпадающих входах — важная деталь: если все кандидаты по
цели одинаковы, различать их по ней нечем, и цель не должна притворяться
значимой. Ноль здесь был бы враньём — он означал бы «худший из пула».

**Шаг 3. Свёртка.** Вклад цели и итог кандидата:

```
вклад(цель)  = нормализованное(цель) * вес(цель)
итог(скор)   = Σ вклад по всем целям / Σ вес по всем целям
```

Деление на сумму весов удерживает итог в `0..1` и делает скоры сравнимыми между
профилями с разными весами. Тот же расчёт, применённый к подмножеству целей
одного эшелона, даёт оценку эшелона (`tier_scores`).

### Расчёт целиком: операция `op_101`

Заявка `op_101`: 15 000 ₽, банк `sberbank`, первая в очереди. Все три внешних
провайдера прошли допуск. Числа ниже — дословно из `routing_decisions.json`,
блок `selection.candidates`.

Сырые значения по целям (строка — цель, столбец — кандидат):

| Цель | эшелон | вес | vipay | payflow | quickpay |
|---|---:|---:|---:|---:|---:|
| `turnover_commitment` | 1 | 1.2 | — | 0.0 | — |
| `count_share` | 2 | 1.0 | 0.4 | 0.35 | 0.25 |
| `volume_share` | 2 | 0.8 | 0.464 | 0.051 | 0.485 |
| `conversion` | 2 | 1.0 | 0.6628 | 0.7114 | 0.5732 |
| `amount_band` | 2 | 0.9 | 0.8 | 0.8 | 0.35 |
| `cascade_priority` | 3 | 0.6 | −1.0 | −2.0 | −3.0 |
| `load_balance` | 3 | 0.7 | 0.36 | 0.0333 | 0.8625 |
| `margin` | 3 | 0.4 | 0.3 | 0.5 | 0.7 |

Нормализация каждой строки по своим `min`/`max`:

```
count_share:       min 0.25, max 0.4,    span 0.15
                   vipay (0.4 - 0.25)/0.15   = 1.0000
                   payflow (0.35 - 0.25)/0.15 = 0.6667
                   quickpay (0.25 - 0.25)/0.15 = 0.0000

volume_share:      min 0.051, max 0.485, span 0.434
                   vipay (0.464 - 0.051)/0.434 = 0.9516

conversion:        min 0.5732, max 0.7114, span 0.1382
                   vipay (0.6628 - 0.5732)/0.1382 = 0.6482

amount_band:       min 0.35, max 0.8,     span 0.45
                   vipay (0.8 - 0.35)/0.45 = 1.0000

cascade_priority:  min -3.0, max -1.0,    span 2.0
                   vipay (-1.0 + 3.0)/2.0 = 1.0000

load_balance:      min 0.0333, max 0.8625, span 0.8292
                   vipay (0.36 - 0.0333)/0.8292 = 0.3940

margin:            min 0.3, max 0.7,      span 0.4
                   vipay (0.3 - 0.3)/0.4 = 0.0000

turnover_commitment: конечное значение одно (payflow, 0.0), span = 0
                   -> все три получают нейтральные 0.5
```

Вклады vipay (`нормализованное × вес`) и итог:

```
turnover_commitment  0.5000 * 1.2 = 0.6000
count_share          1.0000 * 1.0 = 1.0000
volume_share         0.9516 * 0.8 = 0.7613
conversion           0.6482 * 1.0 = 0.6482
amount_band          1.0000 * 0.9 = 0.9000
cascade_priority     1.0000 * 0.6 = 0.6000
load_balance         0.3940 * 0.7 = 0.2758
margin               0.0000 * 0.4 = 0.0000
                                    -------
Σ вклад                              4.7853
Σ вес  = 1.2+1.0+0.8+1.0+0.9+0.6+0.7+0.4 = 6.6

скор(vipay) = 4.7853 / 6.6 = 0.7250
```

В выгрузке у vipay стоит `"score": 0.725`. Тем же способом:
`payflow` — 0.5556, `quickpay` — 0.3788.

Оценки эшелонов считаются той же формулой по подмножеству целей:

```
vipay, эшелон 2: (1.0000 + 0.7613 + 0.6482 + 0.9000) / (1.0 + 0.8 + 1.0 + 0.9)
               =  3.3095 / 3.7 = 0.8945
vipay, эшелон 3: (0.6000 + 0.2758 + 0.0000) / (0.6 + 0.7 + 0.4)
               =  0.8758 / 1.7 = 0.5152
vipay, эшелон 1:  0.6000 / 1.2 = 0.5000
```

Ровно эти три числа лежат в `selection.candidates[0].tiers`.

Поле `score` информационное: в режимах по эшелонам порядок задаётся эшелонами,
а не общей суммой, и совпадение их упорядочений не гарантировано.

## 3. Эшелоны

`tier` — целое число, объявленное у цели в конфигурации. Меньший номер значит
«старше»: эшелон 1 решает раньше эшелона 2. Это способ сказать, что цели
несоизмеримы: обязательство перед партнёром по обороту — не «более важный
процент», а условие другого рода, и складывать его с долей трафика через веса
означало бы утверждать, что 0.1 обязательства эквивалентны 0.3 доли.

Базовая раскладка (`ruby bin/route plan`):

* **эшелон 1** — `turnover_commitment` (вес 1.2): договорные обязательства;
* **эшелон 2** — `count_share` (1.0), `conversion` (1.0), `amount_band` (0.9),
  `volume_share` (0.8): целевое распределение и качество;
* **эшелон 3** — `load_balance` (0.7), `cascade_priority` (0.6), `margin` (0.4):
  тонкая настройка при прочих равных.

Режим согласования — `scoring.mode`:

* `weighted` — эшелоны игнорируются, порядок задаёт общий скор, ничьи разводит
  цепочка `tie_break`;
* `lexicographic` и `lexicographic_weighted` — обрабатываются одной и той же
  ветвью кода (`Scorer#order`), различие выражается не кодом, а конфигурацией:
  строгая лексикографика — это раскладка «по одной цели на эшелон», при
  нескольких целях в эшелоне внутри него неизбежно считается взвешенная сумма.

### `tier_epsilon` и алгоритм кластеризации

`scoring.tier_epsilon` (по умолчанию 0.05) — ширина зоны, внутри которой разрыв
в эшелоне считается отсутствующим. Оценка эшелона — величина, собранная из
нормализаций по пулу; третий знак после запятой в ней не несёт содержания, и
позволять ему решать спор значило бы отдавать решение шуму нормализации.
Поэтому кандидаты, отставшие от лидера меньше чем на эпсилон, объявляются
равными в этом эшелоне, и спор между ними уходит в следующий, где различие
может оказаться содержательным.

Алгоритм `Scorer#rank_by_tiers(ranked, tiers)` словами:

1. Если кандидат один или эшелоны кончились — разрешить порядок цепочкой
   `tie_break` и вернуть.
2. Взять старший из оставшихся эшелонов. Отсортировать кандидатов по его
   оценке по убыванию; при точном совпадении — по идентификатору провайдера
   (сортировка обязана быть полностью определённой, иначе результат зависел бы
   от порядка ключей во входном файле).
3. Пройти отсортированный список слева направо и собрать кластеры. Очередной
   кандидат попадает в текущий кластер, если его оценка отличается от оценки
   **лидера этого кластера** не больше чем на `tier_epsilon`; иначе он
   открывает новый кластер. Сравнение именно с лидером, а не с соседом,
   принципиально: иначе цепочка попарно близких кандидатов склеилась бы в один
   кластер произвольной ширины.
4. Кластер из одного кандидата — готовое место в рейтинге. Кластер из
   нескольких рекурсивно ранжируется теми же правилами по оставшимся эшелонам.
5. Кластеры склеиваются в порядке их появления — порядок старшего эшелона
   сохраняется, младшие эшелоны переставляют кандидатов только внутри кластера.

На `op_101` это видно целиком: в эшелоне 1 все три кандидата получили 0.5,
разрывы нулевые, все трое — один кластер, эшелон 1 не решил ничего. В эшелоне 2
оценки 0.8945 / 0.6937 / 0.2162, разрывы 0.2008 и 0.4775 — оба больше 0.05,
значит три кластера по одному, порядок зафиксирован здесь. Эшелон 3 не
опрашивался вовсе, хотя в нём quickpay был лучшим (0.6471 против 0.5152 у
vipay) — это и есть работа старшинства.

## 4. Разрешение ничьих

Когда эшелоны кончились, а кандидаты остались в одном кластере, порядок
определяет цепочка `scoring.tie_break`. По умолчанию:

```yaml
tie_break: [cascade_priority, conversion, provider_id]
```

`Scorer#tie_break_compare` идёт по цепочке слева направо и возвращает первый
ненулевой результат сравнения. Ключи разбираются так
(`Scorer#compare_by`):

* `cascade_priority` — по полю `priority` провайдера, меньше значит раньше;
  отсутствующий приоритет трактуется как `+∞`;
* `conversion` — по заявленной `conversion_24h`, больше значит раньше;
* `load` — по текущей загрузке, меньше значит раньше;
* `margin` — по разрыву маржи, больше значит раньше;
* `provider_id` — лексикографически по идентификатору;
* любой другой ключ трактуется как идентификатор цели: сравниваются её вклады,
  и если у одного из кандидатов такой цели нет, ключ считается неразличающим.

Первые четыре ключа берут значения **из данных провайдера**, а не из вкладов:
в этой точке нормализованные оценки уже признаны одинаковыми, и опираться на
них второй раз бессмысленно.

Последним всегда идёт идентификатор — и не только потому, что он записан
последним в конфигурации: `tie_break_compare` сравнивает по `provider_id` ещё
раз после того, как цепочка исчерпана, даже если этого ключа в конфигурации
нет. Идентификаторы провайдеров уникальны, поэтому такое сравнение никогда не
даёт нуля, и отношение порядка становится полным.

**Что было бы без него.** `Array#sort` в Ruby не устойчива, и на кандидатах,
неразличимых компаратором, порядок определялся бы деталями реализации сортировки
и исходным порядком элементов, то есть порядком провайдеров во входном файле.
Практические последствия: два прогона на одних и тех же данных могли бы дать
разные `routing_decisions.json`; перестановка двух записей в `providers.json`,
не меняющая ничего по смыслу, меняла бы распределение; воспроизвести чужой
результат и разобрать спорное решение стало бы невозможно. Побайтовая
воспроизводимость двух прогонов подряд проверяется отдельным тестом.

## 5. Решающий фактор

В объяснении выбора указывается не цель с наибольшим вкладом, а цель с
наибольшим **отрывом** от ближайшего соперника (`Scorer#decisive_factor`):

```
для каждой цели g:  отрыв(g) = вклад(победитель, g) - вклад(второй, g)
решающая цель = argmax отрыв(g) среди тех, у кого отрыв > 1e-9
если положительных отрывов нет -> причина "best_combined_score"
```

Причина проста: вопрос, на который отвечает объяснение, — «почему выбрали
именно его, а не следующего». Цель, по которой оба кандидата одинаково хороши,
на этот вопрос не отвечает, каким бы большим ни был её вклад: убери её из
расчёта — и победитель не изменится. Величина `вклад(победитель) − вклад(второй)`
и есть вклад цели в разность скоров, то есть ровно то, что решило спор.

На `op_101` разница видна буквально. Наибольший вклад у vipay — `count_share`
(1.0000). Но отрывы от payflow такие:

```
volume_share         0.7613 - 0.0000 = +0.7613   <- максимум
count_share          1.0000 - 0.6667 = +0.3333
cascade_priority     0.6000 - 0.3000 = +0.3000
load_balance         0.2758 - 0.0000 = +0.2758
turnover_commitment  0.6000 - 0.6000 =  0.0000
amount_band          0.9000 - 0.9000 =  0.0000
margin               0.0000 - 0.2000 = -0.2000
conversion           0.6482 - 1.0000 = -0.3518
```

Поэтому в решении записано `volume_share_deficit` и «решающий фактор против
payflow — volume_share», а не `count_share`. Ответ «выбрали за долю по
количеству» был бы неверен: по доле по количеству payflow отставал всего на
0.33, и одной этой цели не хватило бы. Заодно видно, что по конверсии и по
марже победитель был **хуже** соперника — объяснение не скрывает этого.

Код причины получается отображением идентификатора цели в каталог
`lib/routing/reasons.rb` (`volume_share` → `volume_share_deficit`,
`conversion` → `highest_conversion`, `load_balance` → `lowest_load` и так
далее), поэтому в выгрузке не может появиться причина, для которой нет
словесной формулировки.

Два случая обрабатываются до этого расчёта: если допустимый провайдер был
единственным, причина — `only_eligible_provider` (как в образце организаторов),
а раскладка факторов в `attempts` не пишется вовсе — при одном кандидате все
цели нормализуются в нейтральные 0.5, и таблица из восьми строк изображала бы
сравнение, которого не было. Если это повторная попытка и кандидат остался
один — причина `cascade_retry`.

## 6. Деградация цели

Целевая доля привязана к провайдеру. Если этот провайдер не прошёл допуск,
цель по нему выполнить нечем — и притвориться, что цели не было, нельзя:
отклонение от плана всё равно попадёт в отчёт, и его надо объяснить.

### Перераспределение

Цели по долям нормализуются на **доступное подмножество**
(`Fleet#count_target(id, among:)`, то же для `volume_target`):

```
count_target(i, among: S):
  если S не задано            -> table[i]                     (глобальная цель)
  если i не входит в S        -> 0
  total = Σ_{k∈S} table[k]
  если total <= 0             -> 1 / |S|                      (равномерно)
  иначе                       -> table[i] / total
```

`table` здесь — цели из `traffic_percentage` (для объёма — `volume_share_pct`),
уже приведённые к сумме 1 в `Fleet#normalize_targets`; если во входных данных
сумма долей не равна 100%, они нормализуются и в `data_quality` пишется
замечание.

Подмножество `S` — это `eligible`, список прошедших допуск на текущей попытке
(`Cascade#rank`). Пересчёт происходит на **каждой** попытке каскада, потому что
после отказа пул меняется.

Смысл на примере. Цели 40/35/25. Если payflow не прошёл допуск, оставшимся
достаётся 0.40/0.65 = 61.5% и 0.25/0.65 = 38.5%. Без пересчёта vipay сравнивался
бы с целью 40%, легко её перевыполнял и выглядел бы «нарушителем плана», хотя
выполнять план физически некому — недобор, за который никто не отвечает, тянул
бы вниз обоих оставшихся.

### Событие `goal_relaxation`

`Cascade#relaxation_events` вызывается сразу после жёсткого фильтра, до
ранжирования. `Fleet#unreachable_targets(eligible_ids)` возвращает внешних
провайдеров, которых нет в допущенных и у которых ненулевая целевая доля. Если
такие есть, в `events` решения кладётся запись:

```json
{
  "type": "goal_relaxation",
  "goal": "traffic_share",
  "unreachable": { "payflow": 35.0 },
  "released_share_pct": 35.0,
  "reallocated_to": ["vipay", "quickpay"],
  "note": "целевая доля недоступных провайдеров (payflow) перераспределена между vipay, quickpay"
}
```

Из решений эти записи агрегируются в раздел `goal_relaxations` отчёта: видно,
какие цели и сколько раз пришлось уступить.

### Настройки

Два переключателя управляют разными вещами, и это сделано намеренно:

* `goal_relaxation.enabled` — писать ли событие уступки. Выключение делает
  деградацию молчаливой, расчёт при этом не меняется;
* `goal_relaxation.reallocate_unreachable_share` — пересчитывать ли цели на
  доступное подмножество. При `false` в `Cascade#rank` передаётся `among: nil`,
  цели берутся глобальными, и недоступный провайдер продолжает тянуть
  распределение на себя, оставаясь недостижимым.

По умолчанию оба включены. Оба режима покрыты тестами
(`test/cascade_test.rb`: `test_reallocation_switch_changes_the_target_the_survivor_is_measured_against`,
`test_goal_relaxation_can_be_switched_off_in_configuration`).

## 7. Достижимость цели

Перераспределение (§6) — реакция на то, что происходит в конкретный момент.
Отдельно считается вопрос, достижима ли цель **в принципе** на этой очереди:
`lib/routing/analytics/achievability.rb`, раздел `target_achievability` отчёта.

Расчёт ведётся только по **структурным** ограничениям — тем, у которых
`stateful?` возвращает `false` и которые не зависят от хода прогона:
`provider_status`, `traffic_share`, `amount_range`, `bank_filter`, `margin`,
`currency`. Правила, зависящие от загрузки (`daily_amount_limit`,
`daily_turnover_max`, `in_progress_limits`, `requisites`, `rate_limit`),
исключены: включить их значило бы измерять политику, а не структуру.

Для очереди из `N` заявок и каждого внешнего провайдера `i` считается
`eligible(op)` — множество провайдеров, проходящих структурные ограничения по
заявке `op`, — и три границы:

```
пол(i)                = |{ op : eligible(op) = {i} }| / N
потолок_структурный(i) = |{ op : i ∈ eligible(op) }| / N

потолок_по_ёмкости(i):
  запас = min(daily_amount_limit, daily_turnover_max) - оборот_на_начало_прогона
  запас = max(запас, 0);  если ни одного лимита нет -> потолок = |{op: i ∈ eligible(op)}| / N
  иначе: суммы допустимых для i заявок отсортировать по возрастанию,
         брать подряд, пока накопленная сумма не превысит запас,
         потолок = число взятых / N

потолок(i) = min(потолок_структурный(i), потолок_по_ёмкости(i))
```

Пол — это заявки, где провайдер единственный допустимый: меньше отдать ему
нельзя, не оставив заявку без маршрута. Потолок по ёмкости берёт самые дешёвые
допустимые заявки, потому что именно так достигается максимум по **числу**
операций — никакая стратегия не вместит больше. Запас считается **на начало**
прогона: к моменту сборки отчёта провайдер уже потратил лимит на те самые
заявки, вместимость которых мы оцениваем, и потолок оказался бы ниже факта.

Вердикт:

```
цель > потолок + 1e-9  -> «недостижима сверху»
цель < пол - 1e-9      -> «недостижима снизу»
иначе                  -> «достижима»
```

Для «недостижима сверху» дополнительно собирается агрегат
`blocking_reasons` — какое именно правило и на скольких заявках отсекает
провайдера. Это ответ на вопрос «что менять, чтобы цель стала достижимой».

### `min_total_variation_distance`

Итоговая величина — минимально возможное отклонение фактического распределения
от целевого:

```
min_TVD = ( Σ_i max(0, цель(i) - потолок(i), пол(i) - цель(i)) ) / 2
```

Каждое слагаемое — неустранимая часть отклонения по одному провайдеру: цель
подтягивается к ближайшей границе своего коридора, дальше двигать её некуда.
Деление на два — определение расстояния полной вариации: перебор одного
провайдера всегда сопровождается недобором у другого, и одно и то же
несовпадение не должно считаться дважды.

На данных кейса (`routing_report.json`):

| провайдер | цель | пол | потолок | что ограничивает | вердикт |
|---|---:|---:|---:|---|---|
| vipay | 40.0% | 0.0% | 40.0% | структурные ограничения | достижима |
| payflow | 35.0% | 10.0% | 30.0% | дневной лимит оборота | недостижима сверху |
| quickpay | 25.0% | 30.0% | 90.0% | структурные ограничения | недостижима снизу |

```
min_TVD = ( 0 + (0.35 - 0.30) + (0.30 - 0.25) ) / 2 = 0.10 / 2 = 0.05 = 5.0 п.п.
```

Фактическое распределение прогона — 40 / 30 / 30 при целях 40 / 35 / 25, то есть
отклонение (0 + 0.05 + 0.05)/2 = 5.0 п.п. Роутер попадает точно в доказанный
минимум; заявлять, что «распределение можно улучшить», после этого расчёта
некорректно — улучшать надо лимиты и банковские списки, а не политику.

### При каком допущении граница верна

Формула верна в предположении, что **каждая заявка уходит допустимому внешнему
провайдеру**: только тогда фактические доли внешних провайдеров в сумме дают
единицу и покоординатные границы коридоров складываются в границу на расстояние
полной вариации.

Это допущение не остаётся в документации: оно выписано прямо в отчёте, в поле
`target_achievability.assumption`, рядом с самим числом.

Допущение нарушается при `exhausted_pool_policy: fallback`: часть заявок уходит
на self-провайдера, который стоит вне целевого распределения. Сумма долей
внешних провайдеров становится меньше единицы, и любая доля может опуститься
ниже своего пола — это не противоречие расчёту, а другая постановка задачи, в
которой сравнивать факт с `min_TVD` нельзя. Пол вычисляется как «заявки, где
провайдер единственный допустимый», и его смысл — «меньше отдать нельзя, не
оставив заявку без внешнего маршрута»; при разрешённом уходе на self такой
маршрут перестаёт быть обязательным.

## 8. Каскад и исчерпание пула

### Порядок

`Cascade#route` для каждой заявки:

1. **Допуск.** `hard_filter` проходит все внешние провайдеры и правила в
   порядке конфигурации; каждый исключённый получает запись `skipped` с кодом и
   деталями.
2. **Уступка цели.** `relaxation_events` (§6).
3. **Ранжирование.** `Scorer#rank` по оставшимся; цели по долям считаются на
   доступном подмножестве.
4. **Попытка.** Лучший кандидат получает заявку: резерв состояния
   (`reserve`) → ответ симулятора → списание (`settle_approved`) либо полный
   откат (`settle_failed`). Шаг пишется в `cascade.path`.
5. **Отказ.** Исходы из `simulation.cascade_on` (`rejected`, `expired`) считаются
   отказом в приёме: провайдер выбывает из пула, пишется запись `skipped` с
   `provider_declined` или `provider_timeout`, и цикл повторяется с шага 3 —
   с **новым** ранжированием, потому что состояние изменилось. Ограничение
   сверху — `run.max_attempts` (по умолчанию 3).
6. **Пул исчерпан.** Когда допустимых не осталось (или исчерпаны попытки) —
   политика `run.exhausted_pool_policy`.

Долю трафика получает только итоговый выбор: `record_selection` вызывается один
раз, после того как исход известен. Попытки, кончившиеся отказом, в долю не
входят — иначе провайдер, который много отказывает, «выбирал» бы свою квоту
отказами.

### Что записывается в `attempts`

У каждой записи есть `provider`, `decision` (`selected` / `skipped`), `reason`
(код из `lib/routing/reasons.rb`), `details` (конкретные числа), `stage`
(`hard_filter` / `cascade_attempt` / `ranking` / `fallback`), `sequence`
(порядковый номер в хронологии рассмотрения) и `explanation` (та же причина
словами). У попыток дополнительно `attempt_no`, `outcome`, `latency_sec`, у
выбранного — `score` и полная раскладка `factors`.

Порядок массива — по провайдерам из входного файла, как в образце
организаторов; хронология не теряется, потому что у каждой записи есть
`sequence`, а весь путь каскада лежит отдельно в `cascade.path`. Допустимые
провайдеры, до которых каскад не дошёл, тоже получают запись
(`not_reached_in_cascade`): иначе непонятно, рассматривались ли они вообще.

### `exhausted_pool_policy`

* `retry_best` (по умолчанию) — повторить попытку на лучшем из допустимых.
  Заявка остаётся у внешнего провайдера;
* `fallback` — уйти на self-провайдера (`run.fallback_provider`,
  `spacepayments`).

В обоих случаях в `events` пишется `pool_exhausted` с перечнем отказавших. Если
допустимых не было изначально (пустой пул после жёсткого фильтра), fallback
применяется независимо от политики; если недоступен и он — пишется `no_route`.

### Почему по умолчанию `retry_best`

ТЗ говорит буквально: «Если пул пуст — fallback на spacepayments». Соблазн
сделать дословно велик, но на данных кейса это ломает проверку организаторов.

`data/reference_decisions.json` содержит четыре `deterministic_cases` —
операции, у которых допустимый провайдер ровно один, и любое другое назначение
считается ошибкой: `op_103`, `op_104`, `op_108` обязаны уйти на quickpay,
`op_107` — на payflow. При этом quickpay отказывает именно на этих трёх:
в текущем прогоне `op_103` — `rejected`, `op_104` — `expired`, `op_108` —
`rejected` с первой попытки. Каждый раз он остаётся единственным допустимым, то
есть пул после его выбытия пуст — условие дословного fallback выполняется.
Значит, при `fallback` все три заявки ушли бы на spacepayments, и три
детерминированных проверки из четырёх у `scripts/validate_10.rb` стали бы
красными.

Кроме цены в баллах, дословная трактовка неверна и по существу. «Пул пуст»
и «все отказали» — разные ситуации. В первой маршрута нет, и self-провайдер
последней надежды уместен. Во второй маршрут был, отказала выплата, а не
маршрутизация; уход на self в этом случае прячет проблему и портит аналитику:
конверсия внешних партнёров перестаёт что-либо значить, потому что их отказы
списываются на «нет маршрута».

Поэтому смыслы разведены явно: `retry_best` повторяет попытку на лучшем
кандидате, а на self роутер уходит тогда, когда допустимых нет вовсе. Компромисс
не спрятан: политика переключается одной настройкой, оба режима покрыты тестами
(`test_retry_best_policy_stays_on_external_providers_when_all_refuse`,
`test_fallback_policy_hands_the_operation_to_the_self_provider_when_all_refuse`,
`test_the_two_policies_give_different_answers_on_the_same_input`), а срабатывание
fallback видно в профиле `failover_demo`. В выгрузке повторная попытка помечена
причиной `cascade_retry` с пояснением, почему заявка не ушла на self.

## 9. Соответствие стратегий ТЗ и кода

| № | Стратегия ТЗ | Чему соответствует в коде | Файл |
|---:|---|---|---|
| 1 | Процент от количества заявок | цель `count_share`: недобор `цель × (N+1) − получено`, цель берётся из `traffic_percentage` и нормализуется на доступный пул | `lib/routing/strategies/count_share.rb` |
| 2 | Процент от объёма | цель `volume_share`: тот же недобор в деньгах, цель из `volume_share_pct` | `lib/routing/strategies/volume_share.rb` |
| 3 | Очередь в каскаде | цель `cascade_priority` (порядок по `priority`) плюс сам механизм последовательных попыток; профиль `cascade_only` сводит политику к классическому каскаду | `lib/routing/strategies/cascade_priority.rb`, `lib/routing/cascade.rb` |
| 4 | По сумме чека | цель `amount_band`: полосы сумм из конфигурации либо, если полос нет, специализация провайдера по ширине собственного диапазона. Жёсткий допуск по диапазону — отдельное правило | `lib/routing/strategies/amount_band.rb` (допуск — `lib/routing/constraints/amount_range.rb`) |
| 5 | Приоритизация по конверсии | цель `conversion`: нижняя граница интервала Вильсона по смеси заявленной `conversion_24h` (как `prior_weight` виртуальных наблюдений) и факта прогона | `lib/routing/strategies/conversion.rb`, `lib/routing/statistics.rb` |
| 6 | По интенсивности | жёсткое правило `rate_limit` (скользящее окно `window_sec` по времени заявки, лимит `requests_per_minute_limit`) плюс мягкая цель `load_balance`, где интенсивность входит в загрузку наравне с оборотом, заявками в работе и реквизитами | `lib/routing/constraints/rate_limit.rb`, `lib/routing/strategies/load_balance.rb` |
| 7 | По фин. обязательствам | цель `turnover_commitment` для нижнего обязательства (`daily_turnover_min`), считающая не недобор, а требуемый от остатка суток темп; верхнее обязательство (`daily_turnover_max`) — жёсткое правило | `lib/routing/strategies/turnover_commitment.rb`, `lib/routing/constraints/daily_turnover_max.rb` |

Комбинация стратегий — не отдельный режим, а нормальная работа: все десять целей
(семь из таблицы плюс `margin`) включены одновременно, а их конфликт разрешается
механизмом из §3–4. Именованные наборы перекрытий в `profiles`
(`config/routing.yml`) дают другие политики — с иными эшелонами, весами и
политикой исчерпания пула — без единой правки кода; список и сравнение
распределений выдаёт `ruby bin/route compare`.
