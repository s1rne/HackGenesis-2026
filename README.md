# Умный роутинг выплат

Маршрутизатор выплатного трафика между платёжными провайдерами: для каждой
заявки выбирает партнёра с учётом жёстких ограничений и нескольких
одновременно действующих целей распределения, обходит каскад при отказе,
объясняет каждое решение и по итогам прогона выдаёт аналитику с конкретными
рекомендациями.

Ruby, только стандартная библиотека. Ни одного внешнего гема, ни строчки
машинного обучения — все оценки считаются классической статистикой и
проверяются на бумаге.

---

## Быстрый старт

```bash
ruby bin/route run                  # маршрутизация + отчёт
ruby scripts/validate_10.rb routing_decisions.json    # автопроверка организаторов
```

Больше ничего устанавливать не нужно: `bundle install` отсутствует как класс —
внешних зависимостей у проекта нет.

Нужен **Ruby 3.0 или новее** (проверялось на 3.4 и 4.0). Если запустить более
старым интерпретатором, обе точки входа скажут об этом человеческим текстом,
а не синтаксической ошибкой: проверка версии стоит до загрузки библиотеки.
На macOS системный `/usr/bin/ruby` — это 2.6, нужен `brew install ruby`.

### Команды

| Команда | Что делает |
|---|---|
| `ruby bin/route plan` | показать собранный конвейер: какие ограничения и цели включены, с какими весами |
| `ruby bin/route decisions` | маршрутизировать очередь → `routing_decisions.json` |
| `ruby bin/route report` | аналитика → `routing_report.json` |
| `ruby bin/route run` | оба файла за один прогон |
| `ruby bin/route compare` | прогнать одну очередь всеми профилями и сравнить распределения |
| `ruby bin/route replay` | контрфактический реплей истории: что сделал бы роутер на прошлых 100 операциях |
| `ruby bin/route finalize` | собрать `routing_decisions_test.json` и `routing_report_test.json` и проверить их перед сдачей |
| `ruby bin/route validate` | запустить автопроверку организаторов по собранным решениям |
| `ruby bin/dashboard` | HTML-дашборд объяснимости в `out/dashboard.html` |
| `rake test` | тесты |

Пути к данным переопределяются флагами: `--providers`, `--queue`, `--history`,
`--config`, `--overlays`, `--profile`, `--decisions`, `--report`.

## Как принимается решение

Порядок шагов один и тот же независимо от выбранной стратегии. Ниже — обзор;
формальное описание с формулами, разбором расчёта до последней цифры и
доказательством достижимости целей — в
[docs/decision-policy.md](docs/decision-policy.md).

```
заявка
  │
  ├─ 1. жёсткие ограничения ──────────── допуск: можно ли вообще отправить
  │      11 правил, каждое с кодом причины отказа
  │
  ├─ 2. недостижимые цели ────────────── доля недоступного перераспределяется
  │      факт уступки записывается в решение
  │
  ├─ 3. согласование целей ───────────── кого предпочесть среди допустимых
  │      8 целей, эшелоны, веса, явный тай-брейк
  │
  ├─ 4. каскад ───────────────────────── при отказе — следующий кандидат
  │
  └─ 5. пул исчерпан ────────────────── политика: повтор или self-провайдер
```

### 1. Жёсткие ограничения — допуск

Отвечают на вопрос «можно ли отправить эту заявку этому провайдеру».
Не сравнивают провайдеров между собой, не имеют веса: только допуск или отказ
с причиной. Порядок проверки задаётся конфигурацией, первое нарушение
прекращает проверку и попадает в отчёт как причина.

`lib/routing/constraints/`: статус, выделенная доля трафика, диапазон суммы,
банковский фильтр, дневной лимит оборота, верхнее обязательство по обороту,
лимиты заявок в работе, реквизиты, маржа, интенсивность, валюта.

Новое правило — новый класс-наследник и строчка в `config/routing.yml`.
Регистрация происходит самим фактом наследования; ни каскад, ни скоринг об
этом знать не обязаны.

### 2. Мягкие цели — предпочтение

Отвечают на другой вопрос: «кого предпочесть среди тех, кому уже можно».
Каждая цель возвращает величину в своих единицах — рубли недобора, доля
дефицита, конверсия, номер приоритета, — а сравнимыми их делает нормализация
по пулу кандидатов.

`lib/routing/strategies/`:

| Цель | Что делает |
|---|---|
| `count_share` | доля от количества заявок |
| `volume_share` | доля от объёма в рублях |
| `cascade_priority` | очередь в каскаде по `priority` |
| `amount_band` | предпочтение по диапазону суммы |
| `conversion` | приоритет по конверсии |
| `load_balance` | предпочтение менее загруженным |
| `turnover_commitment` | финансовые обязательства по обороту |
| `margin` | маржинальность для мерчанта |

Две вещи здесь сделаны иначе, чем напрашивается.

**Доли считаются дефицитом, а не жребием.** Бросать кубик с вероятностями
долей на десяти заявках бессмысленно: разброс получается в десятки процентов.
Вместо этого считается, сколько заявок провайдер уже должен был получить к
этому моменту (`цель × (N+1)`) и сколько получил на самом деле. Кто отстал
сильнее — тот и предпочтительнее. Это детерминированный аналог метода
наибольших остатков, разложенный на поток: доли сходятся к целевым с первых
же заявок, а провайдер, временно выпавший из-за жёсткого ограничения, вернёт
свою долю сам, без отдельного механизма компенсации.

**Конверсия оценивается нижней границей, а не наблюдаемой частотой.**
Провайдер с тремя успехами из трёх не лучше провайдера с девяноста из ста,
хотя «сырая» конверсия у первого выше. Нижняя граница интервала Вильсона
разводит их: 0.44 против 0.83. Заявленная `conversion_24h` работает как
априорная оценка весом в 20 виртуальных наблюдений и постепенно вытесняется
фактом прогона — провайдер, отказавший дважды подряд, теряет приоритет сразу.

### 3. Согласование конфликтующих целей

Цели регулярно указывают на разных провайдеров. Просто сложить веса
недостаточно: доля трафика и обязательство перед партнёром — величины разной
природы. Поэтому цели разложены по **эшелонам**, и старший решает раньше
младшего:

1. цели сортируются по эшелонам;
2. внутри эшелона считается взвешенная сумма нормализованных значений;
3. эшелоны сравниваются по очереди; если разрыв в старшем меньше
   `tier_epsilon`, кандидаты считаются равными и спор уходит вниз;
4. остаток ничьих разводит явная цепочка `tie_break` — результат
   воспроизводим и не зависит от порядка ключей во входном файле.

Режим задаётся настройкой `scoring.mode`: `weighted` — одна взвешенная сумма,
`lexicographic` — строго по эшелонам, `lexicographic_weighted` — по эшелонам
со взвешенной суммой внутри (по умолчанию).

Старший эшелон — сильное оружие, и включается он не всегда. Обязательство по
обороту даётся на сутки: «не добрано 2 млн» в девять утра и в одиннадцать
вечера — разные ситуации при одинаковом недоборе. Поэтому цель считает не
недобор, а требуемый от остатка суток темп, и молчит, пока провайдер идёт по
графику. Иначе любое плановое отставание забирало бы весь трафик с первой
заявки дня.

### 4. Недостижимые цели

Если провайдер, которому причитается доля трафика, не проходит жёсткие
ограничения, цель по нему выполнить нечем. Роутер не делает вид, что цели не
было: доля перераспределяется между доступными, а факт уступки уезжает в
решение (`events`) и в отчёт (`goal_relaxations`).

Отдельно считается, достижима ли цель **в принципе**. Для каждого провайдера
по структурным ограничениям выводится коридор:

* **потолок** — доля заявок, которые он вообще имеет право взять;
* **пол** — доля заявок, где он единственный, кто имеет право.

Цель вне коридора недостижима ни при какой политике, и это доказывается
пересчётом. На данных кейса недостижимы сразу две цели:

* `цель 25% на quickpay недостижима снизу, коридор 30..90%` — он единственный
  допустимый в 30% заявок, меньше отдать ему нельзя;
* `цель 35% на payflow недостижима сверху, коридор 10..30%` — у него осталось
  100 000 ₽ дневного лимита, это ровно три заявки из очереди.

Отсюда минимальное отклонение распределения от плана — **5.0 п.п.**,
независимо от того, как хорошо работает роутер. Фактически достигнуто ровно
5.0 п.п., то есть распределение оптимально. Раздел `target_achievability`
в отчёте; там же указано, какое именно ограничение связывает коридор.

Коридор считается в предположении, что каждая заявка уходит допустимому
внешнему провайдеру. При политике `exhausted_pool_policy: fallback` часть
заявок уходит на self-провайдера, и доли внешних могут опуститься ниже пола —
это не противоречие, а другая постановка задачи.

### 5. Каскад и fallback

При отказе провайдера в приёме заявка уходит следующему кандидату, пул
пересчитывается заново — состояние изменилось, и ранжирование вместе с ним.
Когда допустимых не осталось, применяется политика `exhausted_pool_policy`:

* `retry_best` (по умолчанию) — повторить на лучшем кандидате;
* `fallback` — уйти на self-провайдера.

Уход на self-провайдера при отказе по конверсии прятал бы проблему: маршрут
был, отказала выплата, а не маршрутизация, и аналитика по внешним партнёрам
после такой подмены перестала бы что-либо значить. На self-провайдера роутер
уходит тогда, когда допустимых нет вовсе.

### Как увидеть fallback своими глазами

На публичной очереди у каждой заявки есть хотя бы один допустимый провайдер —
это подтверждается эталоном организаторов, — поэтому пул ни разу не остаётся
пустым и `fallback_used` в отчёте равен нулю. Это не значит, что механизм не
работает: ему просто не на чем сработать.

```bash
ruby bin/route run --profile failover_demo \
  --decisions out/routing_decisions.failover.json \
  --report out/routing_report.failover.json
```

В этом профиле провайдеры отказывают часто, и каскад виден целиком:

```
op_101 -> spacepayments (approved)
  1  vipay          skipped   provider_timeout        ответ expired за 512 с
  2  payflow        skipped   provider_declined       ответ rejected за 85 с
  3  quickpay       skipped   provider_declined       других допустимых нет
  4  spacepayments  selected  fallback_self_provider  внешний пул пуст
```

Пять заявок из десяти уходят на self-провайдера. Готовая выгрузка лежит в
`out/routing_decisions.failover.json`.

## Объяснимость

Каждая попытка в `routing_decisions.json` несёт машинный код причины,
человеческую формулировку и конкретные числа:

```json
{
  "provider": "vipay",
  "decision": "skipped",
  "reason": "amount_exceeds_limit",
  "details": "150000 > limit_amount_max 100000",
  "stage": "hard_filter",
  "sequence": 1,
  "explanation": "сумма больше максимального чека провайдера"
}
```

Для выбранного провайдера причина — не «лучший скоринг», а конкретная цель,
которая решила спор с ближайшим соперником: берётся фактор с наибольшим
**отрывом**, потому что цель, по которой оба кандидата одинаково хороши,
ничего не объясняет. Рядом лежит полная раскладка скоринга: по каждому
фактору эшелон, вес, сырое значение, нормализованное, вклад и пояснение
словами.

Порядок массива `attempts` совпадает с порядком провайдеров во входном файле,
как в образце организаторов, а настоящая хронология каскада не теряется:
у каждой попытки есть `sequence`, а весь путь целиком — в `cascade.path`.

Коды причин собраны в одном каталоге (`lib/routing/reasons.rb`), поэтому в
выгрузке не может появиться причина, которую невозможно объяснить словами,
а в отчёте — причина без агрегата.

## Аналитика

`routing_report.json` содержит обязательные разделы (`period`,
`total_operations`, `distribution`, `skip_reasons`,
`projected_daily_utilization`, `recommendations`) и то, без чего по
распределению нельзя сделать ни одного вывода:

* `distribution` — факт, цель и **отклонение** по количеству и по объёму;
* `target_achievability` — достижимость целей, коридоры, причины блокировок;
* `outcomes` — одобрения, отказы, истечения, средняя задержка;
* `provider_performance` — заявленная и наблюдённая конверсия, расхождение;
* `cascade` — глубина, доля спасённых каскадом заявок, срабатывания fallback;
* `limits_at_risk` — что упрётся в потолок раньше остального;
* `goal_relaxations` — какие цели пришлось уступить и почему;
* `history_baseline` — база по истории с интервалами Вильсона;
* `data_quality` — замечания к входным данным и принятые допущения;
* `recommendations_detailed` — рекомендации с параметром, текущим и
  предлагаемым значением, основанием и приоритетом.

Рекомендация вида «стоит улучшить распределение» бесполезна: по ней нечего
сделать. Поэтому каждая запись называет конкретный параметр:

```json
{
  "text": "payflow выбрал 96.7% дневного лимита, свободно 100000 — снизить
           traffic_percentage до 1.2% или поднять daily_amount_limit",
  "parameter": "providers.payflow.traffic_percentage",
  "current": 35.0, "suggested": 1.2,
  "evidence": "оборот 2900000 при лимите 3000000",
  "priority": "high"
}
```

### Контрфактический реплей

`ruby bin/route replay` прогоняет 100 исторических операций через нашу
политику и сравнивает с тем, что было сделано на самом деле. Оценка даётся
**интервалом, а не точкой**: на решениях, совпавших с историей, берётся
фактический исход, а на разошедшихся фактического исхода не существует — там
считается интервал Вильсона по эмпирической конверсии выбранного провайдера.
Выдавать желаемое за действительное на таком сравнении слишком легко, поэтому
результат честно ограничен снизу и сверху.

## Конфигурация

Всё поведение задаётся `config/routing.yml`: состав и порядок правил, состав и
веса целей, эшелоны, режим согласования, цепочка тай-брейка, политика
исчерпания пула, параметры симуляции, пороги аналитики. Код об этих решениях
ничего не знает — он умеет только считать.

**Профили** — именованные наборы перекрытий поверх базовой конфигурации.
Одна и та же кодовая база даёт разное поведение без единой правки кода:

```bash
ruby bin/route compare                      # все профили на одной очереди
ruby bin/route run --profile conversion_first
```

| Профиль | Смысл |
|---|---|
| `balanced` | базовый: доли, конверсия и обязательства в балансе |
| `share_strict` | строго по целевым долям |
| `conversion_first` | максимум одобрений |
| `cascade_only` | классический каскад строго по `priority` |
| `capacity_saver` | беречь лимиты |
| `failover_demo` | демонстрация каскада и fallback |

`config/provider_overlays.yml` — поля, выведенные из истории
(`volume_share_pct`, `requests_per_minute_limit`, обязательства по обороту).
Отдельный файл, а не правка `providers.json`: входные данные организаторов
остаются нетронутыми, наши допущения видно отдельно, и отключаются они одним
флагом `--overlays /dev/null`. Обоснование каждого числа — в
[docs/calibration.md](docs/calibration.md).

## Тесты

```bash
rake test     # 249 тестов, 1664 проверки
rake check    # прогон + автопроверка организаторов + тесты
```

Minitest из стандартной библиотеки, без гемов и без Bundler. Покрыты все
одиннадцать жёстких ограничений по отдельности (срабатывает / не срабатывает
/ неприменимо), все восемь целей, согласование эшелонов, цепочка тай-брейка,
каскад с отказами и fallback, деградация недостижимой цели, откат состояния
после отказа, устойчивость загрузчика к пустым и битым файлам, и
побайтовая воспроизводимость двух прогонов подряд.

Отдельный приёмочный тест сверяет работу жёстких фильтров с эталоном
организаторов: в `data/reference_decisions.json` есть точный список
допустимых провайдеров для каждой из десяти заявок, и движок обязан
воспроизвести его один в один.

Три бага, найденные этими тестами и исправленные, описаны в истории
коммитов: потерянная запись об отказе при повторной попытке, коллизия
синонимов полей и недетерминированность часов при отсутствии времени
во входных данных.

## Устойчивость к входным данным


Решение не привязано к конкретному файлу. Поля ищутся по таблице синонимов
(`payment_system`, `provider_id`, `code` — одно и то же поле), регистр и
разделители не важны, суммы принимаются числом и строкой, список банков —
массивом и строкой через запятую. Незнакомые поля не выбрасываются, а
сохраняются и попадают в отчёт.

Загрузчик не падает на первом кривом поле: берётся разумное значение по
умолчанию, замечание записывается в `data_quality`, и видно, на каких
допущениях построен результат. Падение остаётся только там, где продолжать
нельзя — нет файла, не разбирается JSON, нет ни одной записи.

Отдельная тонкость, которую легко пропустить: поле `exclude_banks` в данных
кейса — булев флаг, задающий, как читать `banks` (`false` — белый список,
`true` — чёрный), а в тексте ТЗ то же поле описано как отдельный список
исключений. Поддерживаются оба прочтения: смысл определяется типом значения.

## Структура

```
bin/route                    точка входа CLI
bin/dashboard                генератор HTML-дашборда
config/routing.yml           все правила, веса и пороги
config/provider_overlays.yml поля, выведенные из истории
lib/routing/
  ingest/                    чтение данных, синонимы полей, замечания
  constraints/               жёсткие ограничения, по файлу на правило
  strategies/                мягкие цели, по файлу на цель
  analytics/                 отчёт, рекомендации, достижимость, реплей
  scorer.rb                  согласование конфликтующих целей
  cascade.rb                 порядок попыток, отказы, fallback
  provider_state.rb          состояние: резерв, расчёт, откат
  statistics.rb              Вильсон, наибольшие остатки, EWMA
  money.rb                   деньги целым числом копеек
test/                        тесты на minitest из стандартной библиотеки
docs/                        ТЗ, калибровка, исследование домена, критерии
```

Деньги хранятся целым числом копеек не из педантизма: суммы лимитов и оборотов
складываются сотни раз за прогон, и на Float сравнение «оборот + сумма больше
дневного лимита» начинает врать ровно на границе — там, где это дороже всего.

## Сдача

```bash
ruby bin/route finalize
```

Собирает `routing_decisions_test.json` и `routing_report_test.json` в корне
репозитория из `data/operations_queue_test.json` и проверяет одиннадцать
условий сдачи: имена, место, структуру, покрытие всех заявок, обязательные
поля. Пока боевой очереди нет, команда собирает заготовку из публичной и
громко об этом сообщает.
